# BHARATPCB — MASTER UI/UX REDESIGN & IMPLEMENTATION PROMPT

## ROLE

Act as a senior Android UI/UX designer, product designer, and Android engineer specializing in professional engineering applications, computer vision tools, industrial inspection systems, and modern native Android UI.

You are working on **BharatPCB**, an Android PCB inspection application integrating:

- YOLO-based PCB defect detection
- PatchCore-based transistor anomaly detection
- ONNX Runtime
- ExecuTorch
- Local LLM-based technical advisory
- Deterministic screening policy
- Inspection history and reporting

Your task is to conduct a comprehensive visual refinement of the existing Android application, implementing a consistent design system throughout the app while preserving its existing architecture and functionality.

I will provide:

- Existing source code
- Existing application screenshots
- Generated redesign reference images
- Design references from other applications

Use these materials to understand the intended direction.

# 1. CORE OBJECTIVE

The existing UI is functional, but some screens feel overly rigid, box-heavy, repetitive, and generic.

The redesign must make BharatPCB feel:

- Professionally designed
- Modern
- Technically sophisticated
- Calm and restrained
- Readable
- Cohesive
- Appropriate for an engineering inspection application
- Premium without being flashy
- Functional rather than decorative

The goal is NOT to create a flashy AI dashboard.

The goal is to create a visually mature engineering application with thoughtful typography, natural spacing, selective surfaces, and a clear information hierarchy.

## Fundamental design principle

**Let typography, spacing, alignment, and subtle tonal contrast do most of the visual work.**

Do not place every element inside a box.

Do not use borders as the primary method of separating content.

Do not treat every section as an independent card.

- Natural
- Soft without being bubbly

- Clean without being empty
- Technical without being cold
- Modern without relying on visual effects

# 4. SELECTIVE CONTAINER USAGE

Containers must be used intentionally.

Use three levels of grouping.

## Level 1 — Open layout (DEFAULT)

This should be the most common layout throughout the application.

Use:

- Background canvas
- Typography
- Spacing
- Alignment
- Simple separators

No card or enclosing surface is necessary.

Appropriate for:

- Settings rows
- Model metadata
- Section descriptions
- History lists
- Advisory content
- Defect lists
- Policy configuration
- Technical details
- Navigation labels

## Level 2 — Soft grouping

Use a subtle tonal surface when several related elements benefit from being grouped.

No prominent outline is necessary.

Appropriate for:

- Warning messages
- Compact supporting information
- Related controls
- Small technical summaries
- Secondary content

## Level 3 — Prominent surface

Use sparingly.

Appropriate for:

- Important inspection disposition
- PCB image preview
- Major inspection summary
- Important readiness information
- Primary context that needs visual separation

Even prominent surfaces should not look like oversized dashboard cards.

### Container rule

If removing a box improves the visual hierarchy without harming usability, remove it.

If a section can be separated effectively using spacing and a simple divider, do not add a card.

# 23. FINAL DESIGN REFERENCE

BharatPCB should look like a carefully designed engineering product.

The final interface must use:

- Dark blue-black palette
- Manrope for large headings
- Inter for interface typography
- IBM Plex Mono for technical information
- Strong but restrained hierarchy
- Open layouts
- Simple line dividers
- Selective surfaces
- Moderate corner radii
- Consistent spacing
- Minimal decoration
- Purposeful iconography

Avoid:

- AI-generated dashboard aesthetics
- Excessive boxes
- Nested cards
- Glowing borders
- Neon
- Glassmorphism
- Decorative gradients
- Oversized pills
- Excessive rounded rectangles
- Visual clutter
- Unnecessary bold text

The application should feel soft but structured, modern but restrained, and technical but readable.

**Do not redesign the application to make it flashy. Design it to make it feel genuinely well-engineered.**

The task is strictly visual.

Do not modify the application's inference, LLM, screening policy, data, storage, or functional architecture.

Start with the audit and proposed file-change plan. Wait for approval before making any code changes.
